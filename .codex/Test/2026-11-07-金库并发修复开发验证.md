## 问题与本次修复

F16 原为安全报告中待验证的 `vault_service.py` 版本号竞争。独立 QA 在真实 Uvicorn TCP HTTP + SQLite 中证实：同一条目同 rev 的两次并发 PATCH 均返回200，后写覆盖前写；空 vault_state 的两条并发新增中出现唯一约束500。原始失败保留在 `/tmp/bypw-independent-qa-20261107/extra.log.before-F16`，本次不将其隐去或改为通过。

修复文件：`backend/app/services/vault_service.py`。新增回归：`backend/tests/test_vault_concurrency_http.py`。没有修改数据库结构、迁移或客户端协议。

- 在数据库事务内以 `INSERT ... ON CONFLICT DO NOTHING` 原子创建每用户 vault_state，再以不改变版本的 UPDATE 持有数据库写锁；同用户的创建、修改、软删、导入、加密设置写入均在该锁内执行。SQLite/ PostgreSQL 有原生冲突处理；其他 SQLAlchemy 方言使用 savepoint+插入冲突处理，但未运行这些其他数据库。
- rev 使用 SQL `UPDATE rev=rev+1 RETURNING rev`；不再以 ORM 的先读后赋值方式递增。锁由数据库事务控制，跨进程生效，没有 Python 全局锁。
- item/folder 修改和删除使用 id、user_id、expected rev、未删除状态的条件 UPDATE。过期版本409、不可访问/已删除记录404，异常回滚整个事务，失败不消耗全局版本号。
- 新增重复请求仍幂等；folder 幂等比较包含排序值；同ID已软删记录不会伪装创建成功。导入保留 skip/overwrite/duplicate 协议；明确 overwrite 按事务顺序执行，重复ID能看见本请求前项；跨账号ID碰撞409并整批回滚，不能留下前半批写入或SQL错误500。
- 设置首次并发写入不再竞争插入同一主键。设置协议没有 expected rev，因此仍为事务顺序的最后写入结果，不额外宣称有设置乐观锁。
- SQLite SQLITE_BUSY/LOCKED（包括扩展错误码）仅有界重试最多3次，每次先回滚，间隔20/40ms，仍失败返回409 `vault_busy`，要求重新同步后重试；数据库已有 busy_timeout=5000ms。不重试任意 OperationalError，不进行无限等待。
