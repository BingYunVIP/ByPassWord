## 结论摘要

这是一个 Vue 3 + FastAPI + SQLite 的个人密码库。在现有测试覆盖的加解密行为中：主密码派生密钥、AES-GCM 记录加密、DEK 包裹、错误密钥解密失败等 17 项前端密码学测试通过；后端 42 项测试也通过。服务端跨用户条目访问在隔离 HTTP 验证中返回 404，未发现从当前代码直接解出历史密码明文的证据。

当前不能按“安全通过”处理。优先修复恢复认证、生产密钥失败开放、SMTP 全局凭据回退、凭证并发消费和本地数据库/备份权限。恢复流程的问题会让取得邮箱验证码的攻击者在未开启 2FA 时替换登录凭据和 DEK 包装值；它仍不等于已经解出历史明文。SMTP 问题只有在部署配置了全局 SMTP 密码且攻击者能让后端连接其自选 SMTP 端点时成立，当前部署是否满足这些条件未知。

## 已证实漏洞

### F-01 恢复认证边界缺失（高）

- 分类：已证实漏洞；证据可信度高；处理状态：待处理。
- 位置：`backend/app/services/auth_service.py:611-660`、`backend/app/schemas/auth.py:146-161`、`backend/app/api/auth.py:273-307`、`frontend/src/pages/ResetPasswordPage.vue:75-88`。
- 触发者与前提：取得目标邮箱验证码；目标未开启 2FA 时不需要主密码或恢复码即可继续。
- 证据：邮箱验证码换取 reset JWT；重置请求不含恢复证明；`reset_password` 只验证 JWT 后直接覆盖 `auth_hash`、KDF 参数、`wrapped_dek` 和 nonce。隔离 T05 返回 `reset_without_recovery=200`、新认证值可登录、包装值被替换；没有使用恢复码，也没有解密历史明文。
- 影响：可取得目标账号 API 权限，读取/替换/删除其密文和设置，并破坏主密码包装完整性。开启 2FA 时本链仍需第二步，不能据此声称绕过 2FA。原恢复包装仍可能用于挽救历史 DEK，不能声称数据必然永久丢失。
- 修复方向：设计服务端可验证但不接收原始恢复码/DEK 的独立恢复证明，绑定账号、单次重置和凭据版本；提交时原子消费。验收要求仅邮箱码、错误/跨账号证明、并发重复重置均拒绝，合法恢复后旧条目仍可解密。

### F-02 reset JWT、2FA challenge 未单次消费（中）

- 分类：已证实漏洞；证据可信度高；处理状态：待处理。
- 位置：`backend/app/core/security.py:54-92`、`backend/app/services/auth_service.py:448-466`、`:642-661`。
- 证据：JWT 虽有 `jti`，但未落库消费；reset 在有效期内可重复提交，2FA challenge 在同一时间步可重复签发 access/refresh。T06 的 reset 重放返回 200；T07 同一 challenge+TOTP 两次均 200；T08 六次错误后正确码仍 200，说明没有按 challenge 计数并作废。
- 影响：有效凭证被复制或竞争时，一次性语义失效；已改密后的旧 reset token 仍可在过期前再次覆盖凭据。
- 修复方向：保存 purpose、user、jti、过期、attempts、consumed 和凭据版本；用条件更新原子消费；改密、注销、2FA 变更时废弃旧 challenge/reset。

### F-03 备用码和 refresh token 并发重复消费（中）

- 分类：已证实漏洞（隔离环境）；证据可信度高；处理状态：待处理。
- 位置：`backend/app/services/auth_service.py:488-505`、`:292-306`。
- 证据：两条路径均先读取“未使用/未撤销”状态，再单独写入。T10 同一备用码并发请求返回 `[200, 200]`；T11 固定同一个 Cookie 的 refresh 并发请求返回 `[200, 200]`。这是受控两请求验证，不是压力测试。
- 影响：单次备用码可能产生多个登录会话；单个 refresh token 的轮换边界可被竞争削弱。不能推断每次竞态都成功或已在生产发生。
- 修复方向：条件 `UPDATE ... WHERE used_at IS NULL`/条件撤销并检查受影响行数；只有成功消费者签发新令牌；定义 refresh token 家族和重放处理。

### F-04 生产默认密钥未失败关闭（高，依赖部署漏配）

- 分类：已证实漏洞（不安全默认配置）；当前部署状态未知；证据可信度高；处理状态：待处理。
- 位置：`backend/app/core/config.py:26-27`、`backend/app/core/security.py:64-92`、`backend/app/core/deps.py:20-25`。
- 证据：生产环境仍可接受公开可预测的 JWT/SERVER 默认值；T14 在隔离实例临时使用默认 JWT 值，对已知合成 UUID 的令牌返回 200。这证实漏配时的后果，不证明当前生产或本机实际采用默认值。
- 影响：若生产漏设 JWT_SECRET 且攻击者取得用户 UUID，可伪造 access token；若 SERVER_SECRET 也漏配，服务端可读的 TOTP/SMTP 密文存在进一步风险。历史 DEK 仍不是由该密钥直接包裹。
- 修复方向：`APP_ENV=production` 启动时拒绝缺失、占位、已知默认、过短或相同的两类密钥；规划 SERVER_SECRET 轮换和既有 TOTP/SMTP 密文迁移。

### F-05 备份和数据库文件权限暴露（中，当前工作区已观察）

- 分类：已证实漏洞（本地文件权限）；证据可信度高；处理状态：待处理。
- 位置：`backend/bypw.db`、`backend/backups/vault-20261105-183905-auto.db`；当前权限分别为 `0644`，父目录为 `0755`，`/root` 为 `0711`。使用本机非特权 UID 65534 检查，两者均可读取。

### F-06 普通账号可调用全库快照且本地副本没有整库加密（中）

- 分类：已证实漏洞（共享备份操作权限与配额边界）；证据可信度高；处理状态：待处理。
- 位置：`backend/app/api/backup.py:20-47`、`backend/app/services/backup_service.py:36-49`。
- 证据：普通账号即可调用 `/api/backup/snapshot`；T13 返回 200，合成快照包含两个账号以及 `auth_hash`、`totp_secret_enc` 等列。快照是普通 SQLite 文件，应用路由没有 age 整库加密，当前 API 只返回元数据，没有下载路由；条目正文仍是客户端密文，不能称所有密码都以明文保存。
- 影响：任意账号可制造全库快照造成磁盘增长；若备份目录被静态服务、主机低权限账号或运维流程暴露，会扩大跨账号数据泄露面。此次未证明远程下载快照。

### F-14 已启用账号可重复 enable 绕过备用码重生成的主密码复核（中）

- 分类：已证实漏洞；证据可信度高；处理状态：待处理。
- 位置：`backend/app/services/auth_service.py:418-445` 与 `:545-565`；`backend/app/api/auth.py:189-199`。

## 业务与信任边界

匿名用户可以预登录、注册、登录和发起恢复。注册账号之间通过 user_id 隔离金库/设置/用户秘密；实现未设管理员角色或首账号后禁注册，而部署文档以个人单用户为定位。服务端全局 SMTP 凭据、全局 SQLite/快照目录属于部署者权限边界；当前普通账号可触达这些共享资源，是 F-06/F-07 的关键。浏览器内主密码→Argon2id→HKDF 分成认证值和包装密钥，随机32字节 DEK 用于记录加密；浏览器外仅发送认证派生值和密文。TOTP/SMTP 为服务端必须读取的秘密，用 SERVER_SECRET 派生的密钥加密。
