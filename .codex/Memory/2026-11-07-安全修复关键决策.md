# 安全修复关键决策

日期：2026-11-07（Asia/Singapore）。

- 用户部署目标为当前WSL仅本机：使用loopback单实例、构建后同源静态前端/API，不暴露Vite开发端口或公网。
- 用户明确选择保留工作区先源码快照不Commit；用户随后明确允许清空项目数据、不备份。已清空旧db/WAL/SHM及旧快照；此明确要求覆盖技能的部署前数据备份默认规则。源码快照非运行数据备份。
- 个人模式默认首账号为部署所有者，首账号完成后停止追加注册；唯一安装owner记录防首次初始化竞态。
- 恢复DEK的本地密钥和服务端恢复验证值用途分离，服务端不接收原始密码/恢复码/DEK。旧账号缺恢复verifier则拒邮箱reset，正常登录不受影响；新建数据部署全部采用新协议。
- refresh采用sid家族、凭据版本与数据库条件消费；2FA/恢复配置变更撤销其他sid，保留当前刚验证会话，主密码修改/重置全量撤销。
- 备份功能使用独立0600密钥AES-GCM整库加密和验证，密钥不放入快照；功能测试仅临时测试数据。用户要求本次切换不做数据备份，正式空库不生成快照。
- 测试证据分层：单元、真实HTTP+SQLite、真实浏览器、真实本地SMTP协议分开；没有真实邮箱配置时不称外部发信验证成功。
- 新发现F15：条目动态验证码原实现为伪算法，改用RFC6238并以独立pyotp/标准向量和浏览器验证；属于用户要求的密码库安全修复。

- 本轮独立QA实际证实原待验证的金库rev并发覆盖/首状态初始化竞态（F16），作为同一修复任务的数据完整性门禁处理；暂停正式部署，修复不得靠单进程Python锁，需数据库事务/条件写入及原子rev，保持客户端协议，不迁移真实数据；修复后由独立QA再次验证真实HTTP和浏览器增改删/导入。
- 宿主低端口阈值1024，正式899服务使用专用非root账号并只授予CAP_NET_BIND_SERVICE，不改全局sysctl，不借此修改其他服务。
