# 开发与协作流程

> 本文档规定"需求怎么进来、任务怎么拆、怎么算做完、什么时候能提交"。
> 与 `.workbuddy-ai/memory/MEMORY.md` 中的协作协议保持一致，冲突时以本文档为准。

---

## 1. 角色

| 角色 | 职责 |
| --- | --- |
| 你（产品负责人） | 提需求、定取舍、在浏览器真实验收、决定是否提交 |
| 我（工程实现） | 需求澄清、方案设计、编码、自测、写文档、按你的决定提交 |
| 子 Agent（可选） | 承担可并行、边界清晰的子任务（如"只做后端认证模块"） |

---

## 2. 需求处理六步（每次都必须走）

### 步骤 1：逐项复述 + 缺口分析

把需求拆成编号条目，逐条写"我理解成什么"。同时主动指出：

- **片面**：只说"加个按钮"但没说点了做什么
- **冲突**：与既有设计系统/架构矛盾（如要求"用红色主按钮"）
- **缺失**：没有空态、错误态、权限、数据迁移、兼容旧数据
- **隐含代价**：性能、安全、维护成本

输出格式：

```
| 需求 | 我的理解 | 假设/风险 |
```

### 步骤 2：提问（仅当会影响实现方向时）

用选择题提问，一次最多 3 个问题。能靠合理默认值推进的，就不要问——写进"假设"即可。

### 步骤 3：任务拆解 → 写入 `docs/TASKS.md`

**每个任务必须包含**：ID、目标、涉及文件、验收标准、依赖、状态。

拆解粒度标准：**一个任务能在一次会话内完成并验证**。太大会烂尾，太小会淹没。

### 步骤 4：实现（可并行）

- 按任务 ID 顺序推进，先做被依赖的。
- 可并行的任务可派子 Agent，规则见第 4 节。
- 每完成一个任务，立刻更新 `docs/TASKS.md` 状态，不要攒到最后。

### 步骤 5：真实冒烟测试

不允许"看起来没问题"。三层测试见第 6 节，全部通过才算任务完成。

### 步骤 6：交付验收 + 提交

1. 给出**手动测试方案**（前置条件 / 步骤 / 预期结果 / 回归范围）。
2. 你验收；不满意 → 回到步骤 4，**不提交**。
3. 你明确说"可以/提交" → 本地 `git commit`（不 push）。

## 3. 任务文档规范（`docs/TASKS.md`）

### 3.1 为什么要有

需求一多，靠对话记忆必然遗漏。任务文档是**唯一事实来源**：

- 我能看到"还剩哪些没做"
- 你能看到"做到哪一步了"
- 新会话/新 Agent 接手时，读它就能继续

### 3.2 状态机

```
TODO → DOING → DONE
         └──→ BLOCKED（写明阻塞原因与需要谁决策）
```

### 3.3 硬性规则

1. **没有验收标准的任务不算任务**——必须可被一条命令或一个操作验证。
2. 任务状态变更**立即**写回文档，不批量补记。
3. 新增需求先入文档再动手；临时插入的也要补登记。
4. 每个阶段结束做一次"对账"：对照需求逐条勾选，确认无遗漏。

## 4. 多 Agent 协作规则

### 4.1 什么时候拆

满足以下**全部**条件才派子 Agent：

- 任务边界清晰（输入输出可写死）
- 与其他任务无文件冲突（不同目录/文件）
- 单任务工作量 > 半天

### 4.2 怎么拆（本项目推荐切分）

| 子任务 | 边界 |
| --- | --- |
| 后端骨架 | `backend/app/core`、`main.py`、健康检查、测试 |
| 认证模块 | `backend/app/api/auth.py`、`services/auth_service.py`、对应测试 |
| 金库同步 | `backend/app/api/{folders,items,vault}.py`、对应测试 |
| 前端加密层 | `frontend/src/crypto/*`、单元测试 |
| 前端数据层 | `frontend/src/api/*`、`stores/vault.js` 改造 |
| 文档/部署 | `docs/*`、`scripts/*` |

### 4.3 并行约束

1. **同一文件不并行**：谁改 `stores/vault.js`，其他人就不能同时改。
2. **接口先行**：并行的前提是 `docs/API.md` 已定稿；任何一方要改契约，先改文档再通知。
3. **主 Agent 负责集成**：子 Agent 只交代码 + 自测结果，集成与最终冒烟由主 Agent 做。
4. **子 Agent 必须更新任务文档**中自己的任务状态。

## 5. 本地开发

### 5.1 端口

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| 前端 dev（Vite） | **899** | `strictPort`，不可自动切换 |
| 后端 API（Uvicorn） | 8000 | 前端通过 Vite 代理 `/api` 访问 |

### 5.2 启动

```bash
# 终端 1：后端
cd backend && . .venv/bin/activate
uvicorn app.main:app --reload --port 8000

# 终端 2：前端
cd frontend && npm run dev      # http://localhost:899
```

> WSL 注意：用 `nohup ... &` 起的进程会随会话退出被杀，长驻请用终端会话或 systemd。

### 5.3 前端代理（`frontend/vite.config.js`）

```js
server: {
  port: 899,
  strictPort: true,
  proxy: { '/api': { target: 'http://127.0.0.1:8000', changeOrigin: true } }
}
```

### 5.4 环境变量

后端 `.env`（不提交）：`DATABASE_URL`、`JWT_SECRET`、`ALLOWED_ORIGINS`。
前端 `.env.local`：`VITE_API_BASE=/api`（默认即可）。

## 6. 测试策略

### 6.1 三层

| 层 | 工具 | 覆盖 | 何时跑 |
| --- | --- | --- | --- |
| 单元/接口 | pytest + httpx | 后端路由、加密工具、TOTP 校验、邮件模板 | 每次改后端 |
| 自动化冒烟 | 无头 Chrome + CDP 脚本 | 真实 DOM 交互、路由守卫、登录/2FA 流程、控制台零报错 | 每次改前端/联调 |
| 手动验收 | 浏览器 | 视觉、手感、边界 | 交付前由你执行 |

### 6.1.1 路由与页面必测项

| 场景 | 预期 |
| --- | --- |
| 未登录直接访问 `/admin` | 重定向 `/login?redirect=/admin` |
| 登录成功后 | 回到 `redirect` 指定页 |
| 已登录访问 `/login` | 重定向 `/admin` |
| 刷新 `/admin` | 静默 refresh 后仍停留，不闪登录页 |
| 开启 2FA 后登录 | 先密码、再验证码；验证码错误 5 次后 challenge 作废 |
| 忘记密码 | 邮箱验证码 → 恢复码 → 新主密码 → 数据仍可解密 |

### 6.2 通过标准（硬性）

- 构建成功（`npm run build`、`python -m compileall` / import 检查）
- 接口测试全绿
- 冒烟脚本 0 失败、控制台 0 报错
- 设计系统清单（`docs/UI-DESIGN-SYSTEM.md` 第 10 节）逐条自检通过

### 6.3 冒烟脚本约定

- 脚本放 `scripts/smoke/`，参数化 base URL，可对 dev / preview / 线上各跑一次
- 断言必须"可失败"（禁止只截图不断言）
- 输出 `PASS/FAIL | 用例名 | 关键值`，失败即非零退出

## 7. 提交规范

### 7.1 何时提交

**只有你明确表示满意之后**。未验收的改动留在工作区，不提交。

### 7.2 粒度

一个逻辑改动一个 commit。互相独立的改动分开提交（例如"字体本地化"与"UI 精简"不混在一起）。

### 7.3 信息格式

```
<type>(<scope>): <一句话说明>

- 变更点 1
- 变更点 2（含取舍原因，便于日后回溯）
```

`type`：`feat` / `fix` / `refactor` / `docs` / `chore` / `test` / `perf`。

### 7.4 禁止

- 不 `push`（除你明确要求）
- 不 `--amend` 已推送的提交
- 不跳过 hook（`--no-verify`）
- 不提交 `.env`、`node_modules`、`dist`、`.workbuddy-ai/`

---

## 8. 完成定义（DoD）

一个任务算完成，必须同时满足：

- [ ] 验收标准全部达成
- [ ] 三层测试中相关层通过
- [ ] `docs/TASKS.md` 状态更新为 DONE
- [ ] 涉及架构/接口/设计系统的变更，已同步更新对应文档
- [ ] 无新增控制台错误、无 lint 级明显问题
- [ ] 交付说明里写清"改了什么、怎么验、有什么风险"

## 10. 文档更新矩阵（改代码时必须同步改文档）

| 你改了什么 | 必须同步更新 |
| --- | --- |
| 新增/修改接口 | `docs/API.md`（先改文档，再写代码） |
| 表结构、字段、索引 | `docs/DATA-MODEL.md` + Alembic 迁移 |

| 任何 UI 元素 | 对照 `docs/UI-DESIGN-SYSTEM.md` 第 10 节清单 |
| 部署方式、端口、依赖服务 | `docs/DEPLOYMENT.md` |
